# Export profile and schedule port

Source review: `health-md` checkout at commit `d30cae82c383dd24c46040876c3f59c862335816`, 2026-10-08. This note distinguishes source behavior from the proposed smaller JavaScript/Expo implementation. The source links below refer to the local checkout.

## Profile contract

A source profile freezes output settings and binds a target; authorization and scheduling are separate concerns. Manual export uses the active profile, while scheduled entries resolve their own profile regardless of activation. Export settings include formats, individual data selection, metadata/detail, filename/folder templates, format folders, and write mode. A schedule belongs to exactly one profile and carries its own cadence and progress; Apple permits at most 100 scheduled entries. Missing profiles disable their schedule rather than substituting the active profile. [Profile model](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Models/ExportProfile.swift:4), [settings snapshot](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Models/ExportSettingsSnapshot.swift:154), [entry model and bound](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Models/ScheduledExportEntry.swift:4), [missing-profile execution guard](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/iOS/SchedulingManager.swift:2720).

## Calendar scheduling

- Apple supports daily, ISO-weekday weekly, and anchored every-N days/weeks/months. Custom interval clamps to 1–365, lookback to 1–30 days, weekly defaults to seven days, and daily defaults to one. Weekly weekdays use Monday=1 through Sunday=7. Android represents all cadences with a unit/value and moves a weekly anchor to the first chosen weekday on or after the saved anchor. [Apple defaults and bounds](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Models/ExportSchedule.swift:80), [Apple calculations](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Utilities/ScheduleDateMath.swift:331), [Android anchored calculation](/Users/codybontecou/dev/health-md/apps/android/app/src/main/java/com/healthmd/data/scheduler/ScheduledProfileEntry.kt:279).
- Cadences and windows use calendar dates and preferred wall time, never multiples of 86,400,000 milliseconds. Apple uses a passed calendar (normally device current); Android stores a zone ID and resolves `LocalDate.atTime(...).atZone(...)`. Monthly occurrences derive every offset from the original anchor, with short-month clamp: January 31 → February 28 → March 31. Iterating from the clamped February date would incorrectly make March 28. [Apple month occurrence](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Utilities/ScheduleDateMath.swift:545), [Android calendar/DST behavior and tests](/Users/codybontecou/dev/health-md/apps/android/app/src/test/java/com/healthmd/data/scheduler/ScheduledProfileOccurrenceMathTest.kt:152), [Android monthly clamp tests](/Users/codybontecou/dev/health-md/apps/android/app/src/test/java/com/healthmd/data/scheduler/ScheduledProfileOccurrenceMathTest.kt:290).
- Next run is strictly after now. Due evaluation selects the latest scheduled boundary at or before now, rather than enqueueing every missed slot. Custom schedules have no occurrence before their anchor. An OS wake can therefore be late without changing its logical occurrence key or data window. [Apple latest occurrence](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Utilities/ScheduleDateMath.swift:179), [Android latest boundary](/Users/codybontecou/dev/health-md/apps/android/app/src/main/java/com/healthmd/data/scheduler/ScheduledProfileEntry.kt:195).
- Apple `enabledAt` records the current enabled period and rejects fire dates at or before opt-in, as well as future/disabled occurrences. Re-enabling starts a new opt-in period. Android's profile entry has no equivalent field, a parity difference; use Apple's explicit gate for this port so enabling after today's time does not immediately export a pre-opt-in occurrence. [Apple eligibility](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Utilities/ScheduleDateMath.swift:63), [enable transition](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Models/ScheduledExportEntry.swift:20), [Android fields](/Users/codybontecou/dev/health-md/apps/android/app/src/main/java/com/healthmd/data/scheduler/ScheduledProfileEntry.kt:56).
- Last successful completed boundary prevents duplicate occurrences, not duplicate owner dates. Every newly admitted boundary exports its entire trailing configured window even when previous occurrences exported overlapping days. This deliberately refreshes previously exported health data. [Apple success recheck and full-window reuse](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/iOS/SchedulingManager.swift:2743), [Android full trailing window](/Users/codybontecou/dev/health-md/apps/android/app/src/main/java/com/healthmd/data/scheduler/ScheduledProfileEntry.kt:230).

## Data windows and Today Refresh

Completed-day exports cover `[fire-day minus lookback, fire-day minus one]` inclusive. A delayed Monday boundary still exports its Monday-relative window even if it executes Tuesday. This is different from the older catch-up helper, which computes uncovered data days relative to execution now and the last run day; the profile occurrence path freezes the full boundary-relative window instead. Do not use the legacy helper to shorten a profile's window. [Window implementation](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Utilities/ScheduleDateMath.swift:244), [legacy catch-up helper](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Utilities/ScheduleDateMath.swift:90), [profile runner](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/iOS/SchedulingManager.swift:2775).

Today Refresh is optional and independent of completed-day cadence. Supported intervals are 3, 6, or 12 hours. Slots are the preferred hour/minute plus whole intervals while hour is below 24; after the last slot the next is tomorrow's preferred time. It does not create a rolling interval across midnight. Due refresh selects only the latest slot in the current calendar day and requires that slot exceed its last refresh success. Its data window is today's partial day. [Refresh date math](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Utilities/ScheduleDateMath.swift:207), [refresh eligibility](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Utilities/ScheduleDateMath.swift:80), [refresh window](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Utilities/ScheduleDateMath.swift:164).

Apple treats completed and refresh as separate occurrence kinds; Android can join today's refresh date to a new completed-day window, but refresh-only success never advances the completed-day marker. Android frozen residual work runs first without adding today's refresh slot. These are implementation differences with the same essential two-progress-marker contract. [Apple kind-keyed coordinator](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Managers/ScheduledExportCoordinator.swift:120), [Android residual priority and refresh composition](/Users/codybontecou/dev/health-md/apps/android/app/src/main/java/com/healthmd/data/scheduler/ScheduledProfileEntry.kt:207), [Android separate progress](/Users/codybontecou/dev/health-md/apps/android/app/src/main/java/com/healthmd/data/scheduler/ScheduledProfileExportWorker.kt:220).

## Durable execution and progress

Prepare and persist a job before beginning export. Apple deduplicates by source=scheduled plus profile ID, kind, and exact scheduled fire date. An existing pending request wins over newer settings or lookback edits. It freezes exact owner dates, settings, target, profile name, and original calendar zone. On partial completion the same request ID retains only unresolved dates; when the result cannot identify completed dates it conservatively keeps the original dates. Locked-device failures preserve work and notify the user. [Prepare/freeze and identity](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Managers/ScheduledExportCoordinator.swift:115), [completion and residual handling](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Managers/ScheduledExportCoordinator.swift:57).

Android also freezes residual settings and destination and processes the oldest residual first. Durable operation IDs distinguish retries of captured artifacts from dates requiring fresh capture. Its worker records partial results/history, checkpoints remaining dates, and retries up to its worker-attempt policy (three threshold), while rearming future occurrences even after failure. Cancellation preserves unresolved completed-day dates; refresh-only cancellation leaves its slot unsatisfied for natural retry. The port can use a simpler durable local job because it has no API/Mac transport, but it still needs exact residual dates and a persistent occurrence identity. [Android freeze/residual groups](/Users/codybontecou/dev/health-md/apps/android/app/src/main/java/com/healthmd/data/scheduler/ScheduledProfileExportWorker.kt:487), [retry/cancellation handling](/Users/codybontecou/dev/health-md/apps/android/app/src/main/java/com/healthmd/data/scheduler/ScheduledProfileExportWorker.kt:324), [rearm after outcome](/Users/codybontecou/dev/health-md/apps/android/app/src/main/java/com/healthmd/data/scheduler/ScheduledProfileExportWorker.kt:115).

Track completion by owner date separately from files written. A data day can generate multiple artifacts; `successCount`, `completedDates`, `failedDateDetails`, and file count are not interchangeable. Full completion must account for all requested dates and cancellation/terminal failures. Advance an occurrence's success marker only after its entire window completes; partial success retains residual work. Persist a date's completion only after every selected format for that date has committed. [Apple result contract](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Managers/ExportOrchestrator.swift:102), [remaining and full-success rules](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Managers/ExportOrchestrator.swift:288), [profile marker advancement](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/iOS/SchedulingManager.swift:2790).

Apple arms one coalesced background wake for the earliest next occurrence across enabled entries using `earliestBeginDate`; this expresses eligibility, not a guaranteed execution time. Logical schedule calculations belong in dependency-free core; OS wake registration, app resume, health reads, filesystem writes, and notifications belong at native/client boundaries. Do not advertise exact-time background delivery. [Coalesced next plan](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/iOS/SchedulingManager.swift:3382), [background request](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/iOS/SchedulingManager.swift:413).

## File behavior and deliberate port scope

Source format selection supports Markdown, Obsidian Bases, JSON, and CSV; JSONL is a new format for this app. Source names support `{date}`, `{year}`, `{YR}`, `{month}`, `{day}`, `{weekday}`, `{monthName}`, and `{quarter}`, with an optional relative folder template and optional format folders. A frozen timezone override drives formatting. Source settings default to overwrite. [Formats and modes](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Models/AdvancedExportSettings.swift:11), [names/folders/date placeholders](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Models/AdvancedExportSettings.swift:487).

Source update mode merges only Markdown and overwrites JSON/CSV. Source append concatenates text blocks with blank lines and suppresses an exact repeated suffix; copying this for JSON would create invalid multi-document JSON. The recommended initial port uses replacement for both JSON and JSONL. If append is exposed, it must be JSONL-only with explicit record identity/dedup semantics; JSON update/append needs structural parsing rather than copied text concatenation. [Mode resolution](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Managers/VaultManager.swift:4480), [text append behavior](/Users/codybontecou/dev/health-md/apps/apple/HealthMd/Shared/Managers/VaultManager.swift:429).

Proposed scope for this app:

- Only JSON and JSONL, using existing native health records and enabled profile data types. Preserve this app's record schema instead of claiming compatibility with health-md's aggregate/detail/archive schemas.
- One settings object per profile for selected formats, filename template, bounded relative folder layout, optional format subfolders, and calendar cadence/window/refresh. Imports and AI/MCP links carry these settings for user review; execution enablement remains explicit on the phone.
- Store output beneath app documents in a profile-specific directory. User folder vaults, arbitrary remote endpoints, Connected Mac transport, archive/Markdown injection, and account quotas are separate features and do not need to be copied to fulfill local file export.
- Reject absolute paths, traversal, empty filename results, unknown placeholders/formats, and filename collisions across dates. Require the rendered output path to remain within its profile root. Native file commit uses a temporary file and replacement before recording progress.
- Keep JSON as a valid standalone document and JSONL as one complete JSON object per line with a trailing newline. Overlapping scheduled windows replace the same daily file so late health records appear without duplicate appended samples.
- Keep persistent pending jobs and bounded history, show pending/running/succeeded/partial/failed state and per-date progress, and provide explicit retry. Profile edits must not silently mutate a previously attempted job. Profile deletion must discard or cancel its pending jobs explicitly.

These scope choices are recommendations for the JavaScript/Expo port rather than claims that health-md already implements them. The exact output schema, document destination, and replacement mode should be documented in the app README alongside its background scheduling limits.
